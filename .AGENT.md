For this system, the best fit is:

Docling for parsing and structured document representation. Docling’s DoclingDocument supports text, tables, pictures, hierarchy, layout/bounding boxes, and provenance, and its pipeline options include OCR, table structure extraction, PDF backends, and threaded PDF processing.
Qdrant for retrieval storage. Qdrant supports hybrid queries that combine dense and sparse vectors with server-side fusion such as RRF, and it also supports multivectors for late-interaction style reranking on long documents.
Haystack for retrieval orchestration and reranking. Haystack supports metadata filtering at query time and provides ranker components for improving retrieval results.
LangGraph only for tightly controlled workflow/state management, not as a free-form autonomous agent. LangGraph is designed for long-running, stateful workflows with persistence and durable execution.

Hierarchical chunking spec

Do not rely on framework-default chunking.

Implement your own chunker with three levels.

Level A: atomic chunks

Purpose: precise recall.

Create from:

paragraphs
single procedure steps
short warning blocks
note/caution blocks
small table row groups
spec entries
caption + figure text

Target size:

80–220 tokens
hard max 300

Payload additions:

chunk_type
chunk_level = 1
parent_section_id
neighbor_ids
Level B: local context chunks

Purpose: preserve enough context for reranking and answer synthesis.

Create by grouping adjacent atomic chunks within the same section.

Target size:

300–800 tokens
ideal 450–650

Rules:

never cross major heading boundaries
never merge body with appendix automatically
keep warnings attached to the nearest relevant procedure block

Set:

chunk_type = section_window
chunk_level = 2
Level C: parent chunks

Purpose: citation and explanation assembly.

Create one chunk for each subsection or procedure block.

Target size:

800–1800 tokens
hard max 2200

Set:

chunk_type = parent_section
chunk_level = 3
Special chunk types
table records

Create:

one table-summary chunk
one row-group chunk per 3–8 related rows
one key-value chunk per spec-style row
procedure records

Create:

one step chunk per step
one grouped procedure chunk per 3–7 steps
one full procedure parent chunk
brochure facts

Implement multi-stage retrieval.

This stage should also decide filter strictness.

Stage 1: metadata prefilter

Use strict filters when explicit identifiers exist:

Examples:

exact product_model
exact manufacturer
document_kind in [manual, datasheet]
is_active = true

Haystack supports attaching metadata to documents and applying query-time metadata filtering to narrow the retriever to the most relevant subset.

Stage 2: parallel retrieval

Run in parallel:

dense retrieval

For semantic meaning and paraphrased questions.

Search:

dense
top 40
sparse retrieval

For exact codes, part numbers, menu labels, UI terms, units.

Search:

sparse
top 40
special-route retrieval

If query class is:

spec_lookup: search only spec_record, table_record, datasheet_record
safety: search only warning_record, procedure_record
how_to: search procedure_record, section_window
brochure_claim: include brochure facts but rank below manuals/specs

Use Qdrant’s hybrid querying with server-side fusion.

Stage 3: fusion

Fuse dense + sparse results with RRF first.

Then deduplicate by:

same parent section
same page span
same logical node group
Stage 4: reranking

Send top 30 fused candidates to a local reranker.

Haystack provides ranker components specifically to improve retrieval ordering.

Recommended behavior:

rerank by content_for_rerank
keep top 8–12
require score separation threshold for “high confidence”
Stage 5: parent expansion

For final answer assembly:

keep exact winning atomic chunk
expand to local context chunk
optionally attach parent section if needed
attach adjacent step or adjacent table rows only when relevant

Do not stuff multiple large parent sections into the final prompt.

Stage 6: answer validation

Require the answer layer to check:

Is every factual claim supported by retrieved evidence?
Are source pages attached?
Did we use a superseded doc accidentally?
Did we answer the actual requested model/version?
Is confidence adequate?

If no:

run one targeted second-pass retrieval
otherwise abstain
Use of Qdrant late interaction

Implement this in phase 2, not day 1.

Qdrant’s multivector support is valuable for long technical documents because single pooled vectors lose token-level detail; multivectors improve precise matching, especially with late-interaction models.
